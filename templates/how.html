How this model works

Everything below is generated from metrics.json, which train.py writes.

1. The two independent parts

ML model: {{ m.model }}. Before anything else, the text is normalised: URLs, e-mail addresses, phone numbers, currency symbols and numbers become placeholder tokens (zzurl, zzemail, zzphone, zzmoney, zznum), and messages with several ALL-CAPS words get a zzcaps token. Two kinds of features are extracted: word and two-word phrases, and character n-grams (3–5 letters inside words). The character n-grams help with misspellings (milion, winer), obfuscation (fr33) and Hinglish spelling variants. Each feature has a learned weight. The spam probability is sigmoid(bias + Σ tfidf × weight), so every feature's contribution can be shown exactly. That's what the highlighting on the main page shows. The model has {{ "{:,}".format(m.n_features) }} features and was trained on {{ "{:,}".format(m.n_train) }} messages (scikit-learn {{ m.sklearn_version }}).

Red-flag rules: hand-written, named patterns for common scams, mostly Indian ones. They are not learned from data, and each one shows what it matched.

Safe signals: hand-written patterns that recognise the format of genuine transactional alerts (bank debit/credit alerts, UPI confirmations with a reference number, OTP texts that say "do not share" and have no link other than the bank's own domain, courier status updates, e-challans that link only to parivahan.gov.in, KYC-complete notices, expense/PO approvals). These exist because the ML model often scores genuine alerts as spam (see limitations).

Official-domain check: real banks, payment apps, telecoms, couriers and government services only link to their own domains. Every link's real host is checked against an allowlist of {{ official|length }} official domains (plus any *.gov.in and *.bank.in). A link to an official domain is a good sign; a host that uses a brand name or a typo of one without being official (sbi-kyc-update.com, hdfcbank.com.verify.xyz, 1cici.co) is a high red flag.

How the final verdict is decided:

  1. If a safe signal matches and no red flag fired and no blocker applies: Not spam (standard alert), or Unsure if the ML score is ≥ 95%. Exception: if the message matches a standard alert format and every link goes to an official domain, it is Not spam (standard alert + official link) even when ML is ≥ 95%.
  2. ML spam probability ≥ {{ (high*100)|int }}% → Spam.
  3. Otherwise, if any high red flag fired → Spam. These rules override the ML score.
  4. Otherwise, if a medium red flag fired and ML ≥ {{ (low*100)|int }}% → Spam.
  5. Otherwise, if ML is between {{ (low*100)|int }}% and {{ (high*100)|int }}%, or a medium flag fired → Unsure.
  6. Otherwise → Not spam.

6. Red-flag rules

The KYC / account / SIM block rule has two forms. With a link or phone number it is high (always Spam). With no link or number, a block/suspension threat plus a KYC/PAN/Aadhaar update demand (for example "Your SBI account will be blocked today, update KYC" or "Aapka account block ho jayega, KYC update karein") is medium: Spam if the ML score is at least 35%, otherwise Unsure. Misspellings (blokd, suspnded, updte, expird) and Hinglish (band / block / suspend ho jayega) are covered. It does not fire on "your KYC is verified/complete" notices, and the no-link form is switched off when the message mentions a branch or visiting one. If the only link is to the bank's official domain and there is no phone number, the rule is medium instead of high.

How domains are matched. Only the end of a web address decides who owns it. netbanking.hdfcbank.com is HDFC Bank (a real sub-domain), but hdfcbank.com.evil.xyz belongs to evil.xyz, hdfcbank-kyc.com is a different site, and in http://onlinesbi.sbi@evil.xyz everything before "@" is decoration. Look-alikes are found by brand names inside the host (short names like sbi, pnb, rbi, jio only at the start or end of a word, so "lesbian" or "turbine" don't count), common digit swaps (0→o, 1→i/l, 3→e, 5→s, rn→m) and, for long names like hdfcbank or flipkart, one typo (hdcfbank, flipkrat). The medium "brand named, link goes elsewhere" rule needs the brand name and a call to action (verify, claim, pay, track...) within about 200 characters of an unrelated link or a URL shortener.

A safe signal is never applied if any of these is true: any red flag fired; the message links to a domain that isn't on the official list ({{ official|length }} bank, payment, telecom, courier, shop and government domains, listed in domains.py and below); it uses a shortened link; it asks you to enter or share a PIN, OTP, password or card details; it asks for a payment or fee; or it urges you to call a number to avoid blocking. Some rules have extra conditions. For example, an OTP message must contain no link except to the bank's official domain, the official-link signal is not applied if the message also gives a mobile number, and a "KYC verified" notice must not mention pending, expired, blocked or click. The UI always says why a safe signal was or wasn't applied.

⚠️ Scammers may imitate this format. A message that copies a real bank alert word for word, with no link or request, would be marked Not spam. That's usually harmless, because a message that asks for nothing can't steal anything, but you should still verify unexpected debits in your bank app, not through numbers in an SMS. The probe group india:alert_lookalike_scams checks that common imitations (alert format + PIN request, fee, look-alike link, "call to block") are still caught, and india:official_domains checks genuine alerts with official links, the same alerts with look-alike links, and scams that add an official link as a decoy (an official link never overrides a red flag).

8. Known limitations

  • Legitimate transactional SMS can look like spam to the ML model. Bank debit alerts, OTPs, KYC reminders and delivery updates share words with promotional and scam messages ("Rs", "account", "KYC", links). Few real, public datasets contain genuine Indian transactional messages, so the model often scores them high. The safe-signal rules fix common formats, but alerts the ML model is ≥ 95% sure about only drop to Unsure, and formats the rules don't cover (for example "please complete your periodic KYC at your branch") can still show as Spam.
  • Hinglish training data is small. Only a few hundred real Hinglish messages are available (mostly from the 2011 IIIT-Delhi set and Indian telecom promos). The Hindi (Devanagari) data is machine-translated from English SMS, and the quality is poor.
  • Newer scam types (digital arrest, CEO fraud, emergency "papa accident" texts, fake customer care) are barely present in public data from 2002–2023. They are mainly caught by the red-flag rules, not the ML model.
  • Email data is old (Enron ~2000–2005, SpamAssassin 2002–2005), so the model may miss modern email phishing styles.
  • A bag of words and character pieces doesn't understand meaning or intent. "I won the match" and "you won a prize" share words.
  • Probabilities come straight from logistic regression and aren't recalibrated for your own mix of messages. Treat 35–65% as uncertain.
  • The domain allowlist is hand-made. A genuine site that isn't on it (a smaller bank's old domain, a brand's new campaign domain, a bank's sister company) can be flagged as a look-alike if its name contains the brand. Banks are moving to *.bank.in, which is always trusted. Punycode / non-Latin look-alike letters (Cyrillic "а") and links hidden behind a brand name in the path (evil.xyz/hdfcbank.com) are not detected by the look-alike rule.
  • This is a learning project. Don't rely on it as your only protection against fraud.
